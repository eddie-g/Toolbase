# PDF Editor

The PDF Editor is the flagship feature of Toolbase. Users upload a PDF, apply edits in the browser, and download the modified file. The key architectural principle is that **the original PDF is never modified client-side** — all edits are stored as a JSON annotation layer in the database and stamped onto the PDF server-side using PyMuPDF at export time.

---

## Editor Variants

There are three editor interfaces, each more capable than the last:

- **`/documents/{id}/edit`** — the original legacy canvas editor.
- **`/documents/{id}/edit-new`** — the current production editor. Uses a canvas layer for rendering and a separate HTML layer for rich text. This is where all active development happens.
- **`/documents/{id}/edit-pdfjs`** — an experimental PDF.js stream-rewrite editor for source-level text manipulation.

---

## Uploading a Document

A `POST /documents` request saves the uploaded file to `storage/app/` and creates a `documents` row. Unauthenticated users can upload — the document ID is stored in the session so it remains accessible without a login. `ProcessUploadedDocumentJob` is dispatched to run OCR and Fitz text extraction in the background. After creation the user is redirected to the `edit-new` interface.

**Monthly limits** apply to authenticated users: 100 uploads and 1,000 editor actions per calendar month, tracked in `user_pdf_monthly_usages`. Exceeding either limit blocks the relevant action.

### Other ways to create a document

Beyond uploading an existing PDF, documents can also be created as:
- A blank PDF (`POST /documents/create-blank`)
- An AI-generated document (`POST /documents/create-ai`)
- From a pre-built guided template (`POST /documents/create-guided-template`)
- A simple invoice generated by Python (`POST /documents/create-simple-invoice`)

## The Annotation Layer

Every editable element on the page is an **annotation object** in the `pdf_state.annotation_data` JSON array. Each annotation has a unique `_uid`, a `type`, page number, PDF-coordinate position and size (`pdfX`, `pdfY`, `pdfWidth`, `pdfHeight`), and style properties (font, size, weight, colour, background, underline, rotation, vertical/text alignment).

### Annotation types

- **`text`** — a free text box. Can carry per-selection rich formatting (bold, italic, colour on individual words) stored in `ann._richHtml`.
- **`image`** / **`signature`** — a placed image or raster signature. Handled identically at export time.
- **`shape`** — rectangle, ellipse, or arbitrary shape with fill and stroke.
- **`line`** — a straight line with optional arrow endpoints.

### Promoted annotations

When the Fitz extraction pipeline has run on a document, existing PDF text can be "promoted" into editable annotations by clicking on it in the editor. Promoted annotations carry additional source-span data (`sourceBlockLeft/Top/Width/Height`, per-span font/size/colour arrays) so that the export pipeline can reproduce the original text appearance faithfully using the same font metrics.

## Saving

### Live save

During editing, changes are periodically flushed to `POST /documents/{id}/live-save`. This updates the `pdf_state` row for the current page/session without generating a download.

### Save and Save As

`POST /documents/{id}/save-edits` commits the full multi-page annotation state. The **Save** button keeps the current filename; **Save As** opens a modal, calls `POST /documents/{id}/rename`, and persists a new `original_name`.

### Working copy snapshots

The editor maintains a lightweight undo/redo history using snapshot endpoints: `create-working-copy-snapshot`, `restore-working-copy`, and `discard-working-copy-snapshot`. These operate on the session-scoped state, not the persisted `pdf_state` rows.

---

## Redaction

**Annotation-layer redaction (edit-new):** Place a solid filled shape annotation (typically a black rectangle) over content. It is stamped at export time exactly like any other shape annotation. This is the recommended approach.

**Source text redaction (edit-pdfjs):** `POST /documents/{id}/edit-pdfjs/redact-source-text` calls `python/pdf-editor/redact_pdfjs_source_text.py`, which physically removes the text drawing operators from the PDF content stream and replaces them with a filled rectangle. The result is written back to `documents.path` — the text is permanently gone from the PDF binary, not just visually covered.

---

## PDF Export

### Downloading an annotated PDF

`POST /documents/{id}/apply-annotations-direct` triggers `apply_annotations_direct_new.py`. The Python script:

1. Opens the clean base PDF (original file with no baked edits).
2. Iterates the annotation data page by page.
3. For each annotation — inserts the font file, then draws text via `page.insert_text` / `page.insert_textbox` (text), stamps image data via `page.insert_image` (images/signatures), or draws geometry via `page.draw_rect` / `page.draw_circle` / `page.draw_line` (shapes).
4. Returns the annotated PDF as a binary download.

### Format conversions

Additional export options are available as separate endpoints, each backed by a Python script:

| Output | Endpoint | Script |
|---|---|---|
| PDF/A | `convert-to-pdfa` | `convert_to_pdfa.py` |
| Word (.docx) | `convert-to-word` | `convert_to_word.py` |
| Excel (.xlsx) | `convert-to-excel` | `convert_to_excel.py` |
| Encrypted PDF | `encrypt-pdf` | `encrypt_pdf.py` |
| Split PDFs | `split-pdf` | `split_pdf.py` |

## Font Handling

PDFs embed their own font programs, most of which cannot be legally re-used to draw new text. The solution is **font substitution**: `config/font_substitutes.json` maps common embedded font names (e.g. `HelveticaNeue`) to open-source equivalents bundled in `python/pdf-editor/fonts/` (e.g. `Arimo`). The export script loads the substitute via `page.insert_font(fontfile=...)` and falls back to a built-in PyMuPDF font name if the substitute is unavailable.

For promoted (source-extracted) annotations, the editor can also attempt to extract and re-use the actual embedded font binary from the PDF. This is handled by `extract_pdf_fonts.py` and cached under `storage/app/`.

## Text Extraction Pipeline

When a PDF is uploaded, `ProcessUploadedDocumentJob` queues two extraction passes:

**Fitz extraction** (`extract_pdf_pymupdf.py`) parses the PDF's content streams and stores the text in the normalised database tables: `pdf_extractions_fitz` → `pdf_extraction_pages` → `pdf_extraction_blocks` → `pdf_extraction_spans`. Each span records font name, size, colour, and bounding box.

**Prepare overlay** (`GET/POST /documents/{id}/prepare-overlay`) is called by the editor on load. It runs the Fitz extraction if not yet cached, then returns the normalised span data to the client so it can render the hoverable "promote to annotation" highlight layer.

**Clean PDF** (`GET /documents/{id}/clean-pdf`) returns a version of the PDF with all text drawing operators stripped while preserving visual layout. This is the base layer displayed behind the editable overlay, preventing the original PDF text from rendering on top of an edited annotation.

## Page Management

- **Reorder pages** — `POST /documents/{id}/reorder-pages`
- **Add blank page** — `POST /documents/{id}/add-blank-page`
- **Rotate a page** — `POST /documents/{id}/rotate-page`
- **Flatten rotations** — `POST /documents/{id}/flatten-rotations` bakes page rotation transforms permanently into the PDF binary.

---

## AcroForm (Interactive Form Fields)

PDFs with interactive form fields are supported separately from the annotation layer. `extract_acro_form_fields.py` maps the AcroForm field tree. Field values are saved to `pdf_acro_form` via `POST /documents/{id}/save-acro-form-state` and restored on load. At export, `apply_acro_form_values.py` fills the fields, or `flatten_acro_form_to_text.py` converts them to static text.

---

## Document Notes

Document notes are sticky pins that appear in the editor UI but **do not export into the PDF**. They are stored in the `document_notes` table with a page/position anchor, a pin style (6 colours × 6 icons), and a freetext body. Full CRUD is available at `GET|POST|PATCH|DELETE /documents/{id}/notes`.

---

## Access Control

A document is accessible if one of three conditions is true:

1. **Authenticated owner** — `document.user_id` matches `Auth::id()`.
2. **Authenticated admin** — `document.admin_id` matches the admin guard ID.
3. **Session access** — the document ID is present in `session['pdf_editor_accessible_document_ids']`, which is populated when an unauthenticated user creates or uploads a document.

The `DocumentController` constructor middleware enforces this on every document route via `authorizeDocumentAccess()`.
